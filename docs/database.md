# PostgreSQL migrations and access patterns

TASK-005 uses `pg` for runtime access and `node-pg-migrate` for versioned schema changes. Runtime code owns pooling, parameterized queries, transactions, health checks, and UUIDv7 generation in `@supademo/database`.

## Local workflow

Start PostgreSQL and copy the local configuration first:

```bash
cp .env.example .env
npm run stack:up
npm run db:migrate
npm run db:health
```

Useful commands:

```bash
npm run db:dry-run
npm run db:rollback
npm run test:integration
```

`db:rollback` reverses only the most recent migration. It is intentionally separate from `stack:reset`; neither command should be pointed at production without an approved migration/recovery procedure.

TASK-008 adds the `queue_idempotency` table in `2026071200100_queue_idempotency.sql`. Apply it before starting the worker:

```bash
npm run db:migrate
```

`test:integration` builds the API and starts it against the local PostgreSQL configuration from `.env`. It is skipped when `DATABASE_URL` or `REDIS_URL` is absent, so unit tests remain runnable without Docker.

## Migration policy

- Migration files use timestamp prefixes and are applied in order with `--check-order`.
- Pending migrations run in one transaction with `--single-transaction` so a failed migration does not leave a partial schema change.
- Every migration must include a reviewed down migration where safe. Destructive down migrations require explicit human approval before use.
- Schema changes must be backward-compatible during rolling deployments: add nullable/additive structures first, deploy code, backfill, then enforce constraints or remove old structures in a later migration.
- The migration runner owns the `pgmigrations` bookkeeping table; application runtime roles must not be granted schema-modification permissions in production.

## Runtime access

```ts
const pool = createDatabasePool({
  connectionString: config.database.url,
  applicationName: "supademo-api",
  onIdleClientError: reportDatabaseError
});

const result = await query<{ id: string }>(
  pool,
  "SELECT id FROM workspaces WHERE organization_id = $1",
  [organizationId]
);

await withTransaction(pool, async (client) => {
  await query(client, "INSERT INTO memberships (workspace_id, user_id, role) VALUES ($1, $2, $3)", [
    workspaceId,
    userId,
    "viewer"
  ]);
});
```

All dynamic values must be parameters. Query helpers do not authorize access: future repositories must include workspace scope and server-side permission checks in every tenant-owned lookup.

The worker's SQL idempotency store uses the same parameterized access boundary. It stores only a bounded idempotency key, job UUID, processing lease, and completion state; job payloads are not persisted in PostgreSQL.

## Identifier and timestamp conventions

- Use `createUuidV7()` for new primary keys. The database stores them as `uuid`; IDs are generated by application code to preserve UUIDv7 semantics consistently across services.
- Use `timestamptz(3)` for persisted timestamps and UTC values from PostgreSQL `now()`.
- Keep `created_at` and `updated_at` on mutable records. Updating `updated_at` belongs to the repository/service operation until a later migration introduces a carefully reviewed trigger policy.
- Do not expose sequential database IDs or use client-provided IDs without validation.

## Health and recovery

`checkDatabaseHealth()` runs `SELECT 1 AS health_check` and returns only health state and latency, not database errors or connection details. Backups, restore drills, RDS roles, and production migration execution are infrastructure follow-ups and are not established by the local migration task.
